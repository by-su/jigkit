# PRD: 체크아웃 이탈 줄이기

## 문제

결제 단계에 도달한 사용자의 38%가 결제를 끝내지 못하고 이탈한다 `[M]`.
이탈의 62%는 **카드 정보 입력 화면**에서 발생한다 `[M]`.

즉 "살 마음이 없는 사용자"가 아니라 **구매를 결정한 뒤 카드 정보 입력 앞에서 멈추는 사용자**가
가장 큰 손실 구간이다. 이 화면이 요구하는 입력의 양·순서·오류 처리가 1차 용의자다 `[J]`.

경쟁사 3곳 중 2곳은 게스트 결제를 제공한다 `[O]`. 다만 게스트 결제가 이 이탈을
얼마나 줄이는지는 확인되지 않았다 `[?]` — 이 PRD는 그 가정 위에 목표를 세우지 않는다.

### 근거의 한계

- 로그는 "어느 화면에서 이탈했는지"만 말한다. **왜** 멈췄는지는 `[?]`.
  → 카드 입력 화면의 필드별 이탈/오류 이벤트를 쪼개 보면 답이 나온다.

## 범위

### 안에 넣는 것

1. 카드 정보 입력 화면의 이탈 원인을 필드 단위로 특정할 수 있게 한다.
2. 특정된 원인 중 입력 부담·오류 처리에 해당하는 것을 개선한다.
3. 게스트 결제를 A/B 테스트로 검증한다 (도입 결정이 아니라 **검증**까지가 범위).

### 밖으로 빼는 것

- **게스트 결제 전면 도입** — 개선폭이 `[?]`. 테스트 결과 없이 회원 체계·주문 조회·
  CS 흐름까지 건드리는 비용을 정당화할 수 없다.
- **결제 수단 추가(간편결제 등)** — 현재 데이터는 "수단이 없어서"가 아니라
  "입력을 못 끝내서"를 가리킨다. 원인 오진 위험.
- **장바구니~배송지 단계** — 이탈의 62%가 그 뒤에 있다. 여기서 얻을 게 가장 적다.
- **결제 PG 교체** — 원인 규명 전 인프라 변경은 순서가 뒤바뀐 것.

## 성공 기준

| # | 기준 | 확인 방법 |
|---|---|---|
| 1 | 카드 입력 화면 이탈을 필드 단위로 분해 가능 | 필드별 focus/error/abandon 이벤트가 대시보드에 나오고, 이탈 62%가 필드별로 합산되어 설명됨 |
| 2 | 결제 단계 전체 이탈률 38% → 30% 이하 | 개선 배포 후 4주 로그, 배포 전 4주와 동일 기준 비교 |
| 3 | 카드 입력 화면 이탈 비중 62% → 50% 이하 | 위와 같은 구간의 단계별 이탈 분포 |
| 4 | 게스트 결제 효과에 숫자가 붙음 | A/B 테스트 완주 후, 결제 완료율 차이 + 신뢰구간. **"개선됨"이 아니라 구간 값이 나와야 통과** |

기준 2·3은 기준 1이 먼저 충족돼야 원인 대응이 가능하다. 순서가 있다.

## 결정하지 못한 것

- `[?]` 게스트 결제의 이탈 개선폭 → A/B 테스트 (성공 기준 4).
- `[?]` 카드 입력 화면에서 멈추는 이유가 **입력 부담**인지 **신뢰(보안 불안)**인지
  → 필드별 이벤트에서 갈린다: 입력을 시작조차 안 했으면 신뢰 문제, 입력 중 오류·재시도 후
  이탈이면 입력 부담. 대응 방향이 완전히 달라지므로 기준 1 없이 개선안을 확정하면 안 된다.
- `[?]` 38%가 업계 대비 나쁜 수치인지 → 벤치마크 없음. 절대 개선폭으로 대체해 판단한다.
- `[?]` 목표치 30%의 근거 → 카드 입력 화면 이탈(전체의 23.6%)의 약 1/3을 회수하면 닿는
  수치라는 산술 `[J]`. 기준 1의 결과를 보고 재조정 대상.

## 구현 단계로 넘길 메모

기획 단계에서 정하지 않았고, 정해서도 안 되는 것들. 구현 단계에서 **검토 대상**으로 받아라.

- 필드별 이벤트 수집을 기존 분석 파이프라인에 얹을지 별도로 뺄지.
- A/B 테스트 분기 지점 (게스트 결제는 진입점만 나누면 되는지, 주문 데이터 모델까지 갈리는지).
- 카드 입력 화면 개선이 프론트 단독으로 끝나는지 결제 API 변경을 부르는지.
